# Milestone 20 — ReHLDS Passes Its Unit Tests on AArch64

**Date:** 2026-08-16
**Toolchain:** `aarch64-linux-gnu-g++` 13.3.0 cross, `qemu-user-static` 8.2.2
**Build:** `cmake -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain-aarch64.cmake -DCMAKE_BUILD_TYPE=Unittests`
**Run:** `qemu-aarch64-static -L /usr/aarch64-linux-gnu ./build-arm64/rehlds/engine_arm64`

```
There were no test failures, but with warnings: 5; Tests executed: 31
```

**31 tests, zero failures.** Exit code 3 — which CI already treats as success. The five
warnings are the expected "SSE4.1/SSE4.2 not supported" notices, correct on a CPU that has
neither.

This covers the portable delta path (all five delta tests), the scalar mathlib, CRC32C's
table fallback, Info strings, unicode, tmessage, security checks and MSG bit I/O.

## 1. Test count by target

| target | tests | excluded, and why |
|---|---|---|
| x86-32 (JIT+SSE) | 33 | — |
| x86-64 (JIT auto-off, SSE) | 32 | `StructOffsets` — i386 ABI freeze |
| AArch64 (JIT+SSE auto-off) | 31 | `StructOffsets`, plus `Length2D` — SSE-only |

Both exclusions are correct rather than convenient:

- **`StructOffsets`** pins `client_t`'s layout to Valve's original 32-bit engine so
  third-party binaries that hard-code offsets keep working. It describes an *in-memory ABI*,
  not a serialized format, and `client_t` embeds `netchan_t` (four pointers), `client_frame_t*`,
  `edict_t*` and two `resource_t`, so every offset legitimately moves on any 64-bit target —
  on AArch64 `chokecount` lands at 9600 rather than 9264. The plugin-compatibility guarantee
  it encodes only exists on i386 anyway, since a 64-bit engine cannot load 32-bit plugins.
  Now `#if defined(__i386__)`.
- **`Length2D`** is defined only in `mathlib_sse.cpp` and its single engine call site is
  already `#ifdef REHLDS_SSE` with a scalar twin (`11-portable-fallbacks.md` §4).

## 2. What had to be fixed — 129 errors, six root causes

Every one was predicted by `04-x86-64-portability.md`. None needed a design change.

| # | cause | fix |
|---|---|---|
| 89 | `osconfig.h` includes `<smmintrin.h>`/`<xmmintrin.h>`/`<x86intrin.h>` unconditionally, from the global precompiled header | gated on x86 |
| 89 | `sse_mathfun.h` includes `<xmmintrin.h>` unconditionally and is pulled in by `precompiled.h`; `sse_mathfun.cpp` had **no guard at all** | both gated on x86 via `REHLDS_HAVE_SSE_MATHFUN` |
| 99 | `NOXREFCHECK` inline asm hardcodes i386 stack layout (`movl 16(%esp), %eax`) | `__builtin_return_address(0)` off i386 — see §3 |
| 8 | `_mm_prefetch` / `_MM_HINT_T0` used ungated in `sv_main.cpp` | `__builtin_prefetch`, which lowers to `PRFM` on AArch64 and `PREFETCHT0` on x86 |
| 1 | `__rdtsc` in `SV_GetChallenge` seeding | `Sys_FloatTime` off x86; the security property is the RNG, not the clock source |
| 1 | `<cpuid.h>` / `__get_cpuid` | `cpuinfo` zeroed off x86 — every flag names an x86 SIMD extension, and consumers already dispatch on it with scalar fallbacks |
| 1 | `crc32c.cpp` includes `"immintrin.h"` unconditionally | gated on x86 |
| — | `MSG_WriteBits` uses SSE but is gated on **`REHLDS_FIXES`, not `REHLDS_SSE`** | see §4 |

## 3. `NOXREFCHECK` was silently broken on x86-64 too

```c
__asm__ __volatile__("movl 16(%%esp), %%eax;" ...)
```

This does not assemble on AArch64 — but it *does* assemble on x86-64, where it reads garbage.
So the diagnostic has been quietly lying on every 64-bit build. `__builtin_return_address(0)`
is portable and actually correct everywhere; i386 keeps its original asm so nothing changes
on the shipping target.

## 4. `MSG_WriteBits`: the scalar twin is not an equivalent

The "enhanced and safe bits writing" block is gated on `REHLDS_FIXES` while using SSE
intrinsics — the mismatch `04-x86-64-portability.md` flagged. The obvious fix, letting
non-x86 fall through to the `#else`, is **wrong**: that branch is the *original* bit writer
with a different `bf_write_t` layout, so ARM64 would silently lose the safety fix that x86
has.

Instead the SSE is reproduced exactly. The 128-bit operations only ever touch the low 64-bit
lane — `_mm_cvtsi32_si128` zeroes the high lane, `_mm_slli_epi64` shifts lanes independently,
and OR-ing a zero high lane leaves `sse_highbits` untouched — so the whole sequence is:

```c
bfwrite.pendingData.u64 |= (uint64)data << bfwrite.nCurOutputBit;
```

with `maxval = (uint32)((1ULL << numbits) - 1)`; the 64-bit shift is also why `numbits == 32`
does not invoke shift UB. The x86 path is left byte-identical so its codegen cannot regress.
`MSG::BitsWritingReading` passes on AArch64, which exercises this.

## 5. Build ergonomics

`REHLDS_ENABLE_JIT` and `REHLDS_ENABLE_SSE` are now forced off automatically when the target
cannot support them, with a `message(STATUS)` saying so. Previously a default 64-bit or
AArch64 configure succeeded and then failed deep in the build with jitasm template errors.
Both default configurations now build and pass out of the box.

## 6. Untested, and a risk to state plainly

**The 32-bit build could not be verified for this change set.** Installing the ARM64
cross-toolchain caused apt to remove `gcc-multilib`, taking `linux-libc-dev:i386` with it, so
no `-m32` compile is currently possible on this host. One package restores it without
disturbing the cross-toolchain:

```bash
sudo apt install linux-libc-dev:i386
```

Every change above is guarded so that i386 keeps its original code path — `__i386__` selects
the old `NOXREFCHECK` asm, the SSE headers, `_mm_prefetch`, `__rdtsc`, `cpuid`, the SSE
`MSG_WriteBits` and the `StructOffsets` test. But *guarded* is not *verified*, and the 32-bit
build is the production target. **It must be rebuilt and its 33 tests re-run before any of
this is trusted.**

## 6b. This is AArch64 **Linux**, not Apple Silicon

Worth stating explicitly because the two get conflated. What was built here is
`aarch64-linux-gnu`: ELF binaries, glibc, GNU ld, Linux syscalls. Apple Silicon is
`arm64-apple-darwin`: Mach-O, libSystem, ld64, BSD syscalls. Sharing an instruction set is
the easy half; none of the platform work transfers, which is why the brief sequences macOS
as a separate later port rather than a variant of this one.

**And on Apple Silicon the current 32-bit build is not merely awkward, it is impossible.**
Rosetta 2 translates x86-64 only — it has never supported 32-bit x86 — and macOS dropped
32-bit support outright in Catalina. There is no native path and no emulation path for an
i386 binary on that hardware.

The consequence for planning: **if Apple Silicon is ever a target, the 64-bit port is not an
optimisation, it is the entire prerequisite.** The same is true of any ARM64 host, since
there is no i386 there either. That reframes the x86-64 work from "portability nice-to-have"
to "the thing that makes every non-x86 target reachable at all".

(The `linux-libc-dev:i386` advice in §6 is specific to this x86-64 Ubuntu host. It has no
analogue on macOS or on an ARM64 Linux box.)

10 zBots connected and playing, rounds running, hit registration working, full
instrumentation functional. `qemu-aarch64-static -L /usr/aarch64-linux-gnu ./hlds_linux`.

Three more fixes were needed beyond §2, all the same class:

- `DebuggerBreak()` in ReGameDLL (`public/tier0/platform.h:45`) and `DEBUG_BREAK()` in
  `filesystem/FileSystem_Stdio/src/pathmatch.cpp:84` both emit the x86 `int3` instruction.
  AArch64 spells it `brk #0`; `__builtin_trap()` covers anything else.
- The **root** CMakeLists derived `ARCH_FLAG` from `REHLDS_TARGET_BITS` alone, so every
  subproject still got `-m32` under an AArch64 toolchain file. Architecture is now decided
  once at the top and the subprojects follow it, including `-mtune/-msse3` and
  `-fcf-protection` (x86 CET), and the PIC decision for `filesystem_stdio`.
- `ENGINE_LIB` needed an `__aarch64__` arm so the launcher `dlopen`s `engine_arm64.so`.

ReGameDLL cross-built with **one** change (the `int3` above) — `cs_arm64.so` via its existing
`XASH_COMPAT` path.

**The timing numbers say nothing about ARM64 performance.** This is qemu-user emulation, and
`SV_Physics` at 7.06 % of wall against ~2 % natively is the emulation tax; the p99 of 2003 µs
is exactly two periods, i.e. occasional frames whose physics overran the budget under
emulation. What the numbers *do* show is that the scheduler logic is architecture-neutral:
p50 interval 999.9 µs and lateness p50 of 5 µs, even with a 3-4x slower CPU underneath.

## 7. What this does not establish

- **Emulated, not real hardware.** Nothing here measures ARM64 performance, and qemu-user
  papers over memory-ordering issues that real weakly-ordered hardware would expose.
- **Under qemu-user**, not real hardware. Emulation is faithful enough for correctness but
  says nothing about performance, and it papers over some memory-ordering issues that real
  weakly-ordered hardware would expose. The atomics/ordering audit in
  `04-x86-64-portability.md` §14.2 is still outstanding.
- **The 18 unaligned accesses from `17-sanitizers.md` are still there.** AArch64 Linux
  permits unaligned normal loads so they did not break these tests, but they remain UB and
  remain a hazard if the optimiser starts assuming alignment.
- No NEON anywhere; the scalar paths are what runs. That is the correct order — the brief
  requires portable correctness before SIMD, and profiling before either.
