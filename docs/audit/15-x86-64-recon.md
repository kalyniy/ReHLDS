# Reconnaissance 15 — What Actually Breaks in an x86-64 Build

**Date:** 2026-08-16
**Method:** attempt a real `-m64` compile of the engine and inventory the output, rather than
inferring the port's task list from source reading.

> **This does not produce a working 64-bit server and is not claimed to.** It establishes,
> with compiler evidence, which of the predicted blockers are *compile-time* and which are
> not. `REHLDS_TARGET_BITS=64` is labelled experimental in CMake for exactly this reason.

---

## 1. Headline: the engine compiles for x86-64

**All 101 translation units build as ELF 64-bit x86-64 objects. Zero source-level compile
errors.**

```
$ file build64/rehlds/CMakeFiles/engine.dir/engine/sv_main.cpp.o
... ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

This required, in total:

1. `-m64` instead of `-m32`, and `CMAKE_POSITION_INDEPENDENT_CODE ON` — a `.so` without PIC
   merely works by accident on i386 and cannot link on x86-64.
2. `REHLDS_ENABLE_JIT=OFF`, `REHLDS_ENABLE_SSE=OFF` (added in `11-portable-fallbacks.md`).
3. Dropping `HAVE_OPT_STRTOOLS` and the `aelf32` link, since asmlib is a 32-bit-only static
   archive with no source in tree. `public/strtools.h:108+` provides a complete libc
   fallback.
4. **One** source change:
   ```c
   // rehlds/engine/info.cpp:98
   size_t valueLen = Q_min((size_t)(s - value), (size_t)(MAX_KV_LEN - 1));
   ```
   `s - value` is `ptrdiff_t` — `int` on i386, `long` on LP64 — so the two arguments stop
   sharing a type and `Q_min` (a template) fails to deduce.

That is the entire compile-stage cost.

**This substantially reframes the brief's §3 assertion that "a 64-bit build is a genuine
port, not a flag removal."** At the *compile* stage it is very nearly a flag removal. The
statement remains true overall, but the real work is at link and runtime, not compilation —
which is a materially different task list from the one the brief anticipated.

## 2. Link stage: one blocker left

After removing `aelf32`:

```
/usr/bin/ld: cannot find -lsteam_api: No such file or directory
```

**`libsteam_api.so` is the single remaining obstacle to producing an ELF64 engine binary.**
The bundled one is `ELF 32-bit LSB shared object, Intel 80386`, and no 64-bit build of it
exists anywhere in the local Steam installations (`hlds/linux64/` contains `steamclient.so`
and `libsteamwebrtc.so`, but no `libsteam_api.so`).

The stub surface is small and now known exactly — **15 external Steamworks symbols**:

```
SteamAPI_Init                    SteamAPI_RegisterCallback
SteamAPI_RunCallbacks            SteamAPI_SetBreakpadAppID
SteamAPI_Shutdown                SteamAPI_UnregisterCallback
SteamAPI_UnregisterCallResult    SteamAPI_UseBreakpadCrashHandler
SteamApps                        SteamFriends
SteamGameServer                  SteamGameServer_Init
SteamGameServer_RunCallbacks     SteamGameServer_Shutdown
SteamUser
```

(The other 25 Steam-named undefined symbols are ReHLDS's own `Steam_*` functions, defined
elsewhere in the engine.)

Two routes, and this is a genuine decision rather than a technicality:

- **A 64-bit Steamworks redistributable.** Correct for production, but obtaining it means the
  partner SDK, and the legacy `ISteamGameServer` interface versions this engine expects must
  still be present in a modern SDK. Unverified.
- **A stub for `-insecure` LAN development.** 15 symbols is a few hours' work. It yields no
  authentication, so it is useless for production — but the brief's own risk-register
  mitigation says to "isolate Steam behind a compatibility layer; maintain insecure/LAN test
  mode for core development", which is exactly this. It would unblock runtime
  reconnaissance, which is where the real blockers live.

Recommended: the stub, explicitly scoped as a development artifact, tracked separately from
any production Steam story.

## 3. Two genuine LP64 defects surfaced by the compiler

Only two warnings appeared across the whole engine, and both are real.

### 3.1 A function address passed as `uint32` — **not previously identified**

```c
// rehlds/engine/sys_dll.cpp:697
const char *FindAddressInTable(extensiondll_t *pDll, uint32 function)
...
// :708
if (dladdr((void *)function, &addrInfo))
```
`warning: cast to pointer from integer of different size [-Wint-to-pointer-cast]`

A code address round-tripped through a 32-bit integer. Truncates any address above 4 GB,
silently. The portability sweep found the analogous `Sys_MakeCodeWriteable(uint32 startaddr, ...)`
but **missed this one**, which is worse because it is on a live diagnostic path rather than
in `NOXREF` code.

### 3.2 A pre-existing underflow that is identical on both architectures

```c
// rehlds/engine/sv_main.cpp:3213
unsigned char data[4096];
len = 2044 - sizeof(data);
```
`warning: overflow in conversion from 'long unsigned int' to 'int' changes value from '18446744073709549564' to '-2052'`

`sizeof` is unsigned, so `2044 - 4096` underflows, and the result converts to `-2052`.
**The same thing already happens on i386** (32-bit unsigned wrap gives the same `-2052`), so
this is not a regression — the 64-bit compiler simply notices. `len` is an in/out parameter
to `pfnConnectionlessPacket` whose initial value appears unused, and the subsequent
`if (len && len <= 2044)` guards the result.

**Deliberately not changed.** It is pre-existing, architecture-neutral in effect, and
altering it would be a behaviour change without evidence that anything depends on the
current value. Recorded for the port's cleanup pass.

## 4. What this does *not* establish

Compiling is not working. Every blocker in `04-x86-64-portability.md` that matters is a
**runtime or ABI** problem and would not appear until the server runs:

| blocker | surfaces at |
|---|---|
| `string_t` as a truncated 32-bit pointer offset | runtime, on first `ALLOC_STRING` beyond 4 GB from `pr_strings` |
| `edict_t` / `entvars_t` layout | first GameDLL call — and needs a 64-bit ReGameDLL to even attempt |
| `.hpk` custom-content format embedding `resource_t` pointers | first custom-content read/write |
| `DWORD` = 8 bytes on LP64 Linux | wherever it reaches a fixed layout |
| bitfields with `size_t` base in `rehlds_messagemngr_impl.cpp` | struct size change |

Also untouched: the dedicated launcher, filesystem and HLTV sub-projects were not built for
64-bit here (only the engine), and **ReGameDLL_CS has not been built 64-bit at all** — though
per `04-x86-64-portability.md` it already has `XASH_COMPAT` scaffolding for it, which ReHLDS
lacks.

## 4b. ReGameDLL builds 64-bit today — and shows how `string_t` is meant to be solved

```
$ cmake -DXASH_COMPAT=ON -B build64 && cmake --build build64
$ file build64/regamedll/cs_amd64.so
... ELF 64-bit LSB shared object, x86-64
```

**Zero errors, no source changes.** The GameDLL half of the port is already done upstream.

More importantly, `regamedll/dlls/qstring.h:37-88` reveals the intended solution to blocker
**B1** (`string_t` as a truncated pointer offset), and it is *not* widening the type:

```c
#if XASH_64BIT
	using qstring_t = int;          // still 32 bits -- but SIGNED
#else
	using qstring_t = unsigned int;
#endif
...
#if XASH_64BIT
// Xash3D FWGS in 64-bit mode has internal string pool which allows mods to continue use 32-bit string_t
inline int MAKE_STRING(const char *str)
{
	ptrdiff_t diff = str - STRING(0);
	if (diff >= INT_MIN && diff <= INT_MAX)
		return (int)diff;
	return ALLOC_STRING(str);          // graceful fallback when it does not fit
}
#endif
```

The ecosystem's answer is: **keep `string_t` 32-bit, make it signed, and have the engine
guarantee every string lives within ±2 GB of `pStringBase`** by routing them through one
internal pool. Mods keep the existing ABI.

**ReHLDS is already half-compatible with this without knowing it.** `AllocEngineString`
(`pr_edict.cpp:664`) already returns `int` — signed, 32-bit — matching ReGameDLL's
`qstring_t` on 64-bit exactly. The ABI does not need to change.

What ReHLDS lacks is the *range guarantee*. Today:

- `pr_strings = gNullString` (`sv_main.cpp:6371`), a string literal in the engine's own
  read-only data.
- Entity strings come from `Ed_StrPool`, a 128 KB block inside the **hunk**
  (`ed_strpool.cpp:53-54`), which is a separate large allocation.
- Other `string_t` values are offsets to strings that live in neither place —
  `sv_main.cpp:6532,6542-6543` computes offsets to `g_psv.worldmodel`, `g_psv.name` and
  `startspot`.

On i386 the truncation is harmless because everything is 32-bit anyway. On x86-64 the
distance between the engine's `.rodata` and an mmap'd hunk is unbounded under ASLR, and the
model/map name strings are unbounded relative to both.

**So B1 reduces from "break the GameDLL ABI" to "route every `string_t` through one bounded
pool"** — which is a self-contained engine change, is what Xash3D FWGS already does, and
which ReGameDLL's 64-bit build is already written to consume, complete with an
`ALLOC_STRING` fallback if an offset ever fails to fit. That is a materially smaller and
lower-risk task than `04-x86-64-portability.md` §B1 assumed.

Note the corollary: simply pointing `pr_strings` at the hunk base is **not** sufficient,
because of the model/map-name offsets above. The pool has to actually own every string.

## 5. Revised sequence for M6

1. **Steam stub** (15 symbols, §2) → first ELF64 engine binary. Scoped explicitly as an
   `-insecure` development artifact.
2. ~~64-bit ReGameDLL~~ — **already done** (§4b). `cs_amd64.so` builds with
   `-DXASH_COMPAT=ON` and no source changes.
3. **Bounded string pool** (§4b) so every `string_t` is a signed 32-bit offset from
   `pStringBase` within ±2 GB. This is the shape of B1's real fix, it needs no GameDLL ABI
   change, and ReGameDLL already consumes it.
4. Then the remaining runtime blockers in §4 — `edict_t`/`entvars_t` layout reconciliation,
   `.hpk` serialization, `DWORD` width — with ASan/UBSan on, which is where the effort
   actually is.
5. Adopt ReGameDLL's `LibraryNaming.cmake` scheme and finally use the dead `SO_ARCH_SUFFIX`
   in `common/port.h:112-116`, so 32- and 64-bit engines can coexist.

The compile-stage work this document set out to inventory turned out to be done already, and
step 2 turned out to be done by upstream. The port is meaningfully closer than
`04-x86-64-portability.md` concluded — though "closer" still means the runtime ABI work in
step 4 is untouched and unestimated.
